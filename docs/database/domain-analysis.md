# Анализ предметной области

Лабораторная работа №4: проектирование базы данных приложения управления задачами.
Предыдущие требования сквозного проекта не предоставлены; принята предметная область
из задания. Работа ограничена моделированием данных, без реализации интерфейса приложения.

## Функциональные требования

1. Хранить пользователей с уникальными логинами и email.
2. Создавать проекты, у каждого ровно один владелец.
3. Назначать задаче одного исполнителя; проект необязателен.
4. Хранить заголовок, описание, срок, приоритет, статус и время создания/изменения задачи.
5. Присваивать задаче несколько категорий и меток; использовать их повторно.
6. Искать задачи по исполнителю, проекту, сроку и статусу.
7. Сохранять целостность данных при удалении связанных объектов.

## Сущности и связи

| Сущность | Ключ | Назначение |
| --- | --- | --- |
| Users | user_id | Учётная запись |
| Projects | project_id | Группа задач, владелец user_id |
| Tasks | task_id | Работа, исполнитель user_id |
| Categories | category_id | Глобальная категория |
| Labels | label_id | Глобальная метка с цветом |
| Task_Categories | (task_id, category_id) | Связь задач и категорий |
| Task_Labels | (task_id, label_id) | Связь задач и меток |

- Users 1 → 0..N Projects; Users 1 → 0..N Tasks.
- Projects 0..1 ← 0..N Tasks: задача может существовать без проекта.
- Tasks M:N Categories и Tasks M:N Labels через таблицы связей.
- Каждая запись таблицы связей ссылается ровно на одну задачу и один элемент справочника.

## Бизнес-правила и границы

Владелец проекта и исполнитель задачи могут различаться: например, Алексей владеет
проектом «Работа», а Мария выполняет задачу №4. Это намеренное правило, отражённое
в seed и тестах. Из него НЕ следует зависимость project_id → Tasks.user_id.
Авторизация доступа, членство в командах и хранение паролей в эту лабораторную не входят.
Названия категорий/меток глобально уникальны; названия проектов могут повторяться.

При удалении пользователя удаляются его проекты и назначенные ему задачи. Задачи
других исполнителей из удаляемых проектов сохраняются без проекта. При удалении
задачи, категории или метки каскадно удаляются соответствующие строки связей.
Удаление категории/метки не удаляет задачи.

Даты сроков приложение передаёт как ISO 8601 YYYY-MM-DD либо NULL; календарную
валидность проверяет приложение. Временные отметки хранятся как UTC-текст SQLite.
При UPDATE приложение явно устанавливает updated_at = datetime('now'); автоматического
триггера нет. Email хранится как уникальная непустая строка, без проверки почтового адреса.
Регистронезависимая идентификация пользователей в этой модели не заявлена.
